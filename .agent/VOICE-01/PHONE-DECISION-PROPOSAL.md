## Recommendation for a reviewable owner decision

Use **owner-approved, one-time QR association of the iPhone to one existing desktop-selected vault and workspace**, followed by an authenticated, store-and-forward transport on the **existing backend package/host only if host, TLS, storage and recovery gates pass**. The desktop native vault adapter remains the sole canonical writer for this first phone slice. The phone saves exact originals and a durable operation manifest in app-private storage before saying “Saved on this phone”; the relay can acknowledge encrypted durable receipt; only the desktop's journaled, source-hash-verified import may say “In your vault.” It then publishes the ordinary Recall note/history/source. The desktop also emits a bounded encrypted committed-revision/source feed for phone read-only projection; the phone verifies it before showing memory or selecting evidence for Ask. The phone can capture while desktop is off and sync after both are online; it cannot promise a new memory or answer before desktop commitment.

This is the smallest path that meets “capture on phone, remember on desktop” without a sign-in or paid Obsidian Sync. It reuses the Python backend package, device-scope checks, request/receipt patterns, desktop native vault journal, and Expo private-file outbox *as implementation patterns*. It does **not** reuse the legacy Supabase account/token/DB-authoritative upload contract as target authority. It does **not** treat existing PAIR-01 `photo_inference` or `vault_intelligence` grants as sync grants. A separate `vault_sync` permission, owner approval, revocation and replay-safe receipts are needed. QR is a proposed interaction, not an existing authorized capability.

## Actual starting point and trust boundary

Browser/mobile and explicit desktop legacy mode retain Supabase email authentication. The current Expo `services.ts` creates Supabase auth and upload sync; `CaptureScreen` requires a user ID. `ExpoFiles` uses app-private documents, but its physical iPhone durability has not been proved. Mobile config has camera/photo permissions, microphone disabled, and development bundle ID `com.example.recall.dev`.
- PAIR-01 only approves one existing owner/workspace/device/vault for selected-photo inference; manual operator invitation, keyring secret, exact scope and fixed HTTPS origin. The current DO inference profile registers pairing and selected-photo routes, has no original storage, legacy worker, capture/sync API, or public vault bridge. Extending its operational profile to relay is a **new scope and security review**, not a flag flip.
- The DO operations files are synthetic/source evidence. Live host capacity, DNS/TLS, private database readiness, backup destination and deployed API are **UNKNOWN**. The historical HTTPS Caddy pilot overlay is a different legacy topology. An unsigned Expo JS export is not an installed iPhone app. Neither PWA storage nor background sync is established on iPhone.

## First end-to-end transport contract

1. **Associate.** An already trusted desktop/native owner session displays a short-lived QR invitation bound to the selected vault, workspace, invited phone challenge and proposed `vault_sync` scope. Phone creates its device secret in iOS protected storage, displays/returns a fingerprint, and owner explicitly confirms it on the trusted desktop. No persistent credential in QR; expiration, replay, wrong-vault/phone and altered-origin cases fail closed. Server records only a revocable device-key verifier and grants narrowly scoped endpoints; every request checks current membership and revocation. The trusted desktop can revoke a lost phone. If owner declines QR, use a separately reviewed manual same-fingerprint association; do not fall back to anonymous enrollment or email sign-in.
2. **Save locally.** Phone photo/text/voice/file adapters each save the exact selected original and bounded manifest under an operation ID before showing success; protect the phone copy until canonical vault receipt. Reuse the current outbox recovery ideas only after removing their `ownerUserId`/legacy upload authority assumptions. Force-close, low-storage and reinstall behavior need device evidence. Device loss before relay/vault acknowledgement can lose that sole local copy and must be stated honestly.
3. **Relay.** Phone sends versioned, authenticated envelopes and encrypted original chunks through fixed HTTPS to a device/vault-scoped API. Use bounded quotas, size/type validation, idempotent operation/content hashes, retention and backpressure. The relay stores ciphertext blobs plus operational receipt/lease state; it cannot read vault keys or commit notes. A dedicated bounded disk/object store and backup/retention plan are required; do not put broad media blobs in PostgreSQL or assume the existing DO disk is sufficient. The existing backend package may host these endpoints, but the present inference-only API profile and activation preflight must be deliberately extended and re-reviewed. No new Redis/queue/microservice is required by this proposal.
4. **Commit and return evidence.** Desktop pulls authorized pending envelopes, decrypts/validates original bytes, checks operation parent/vault identity and current tombstone/revision, and commits via the same vault journal and direct-edit reconciliation as local capture. It emits a durable desktop-authenticated commit receipt bound to original hash, memory ID, revision and event hash. Phone advances from relayed to vault-committed only after verifying that receipt; duplicate/delayed/conflicting operations reconcile without silent overwrite. A bounded encrypted committed-revision/source feed lets the phone build a read-only, verified local projection for Recent, source opening and Ask evidence selection. Fresh Ask still needs separate Ask-purpose consent/grant and an approved provider request; the phone must revalidate citations against the committed feed and show abstention when evidence is absent/stale. Lost/revoked devices cannot fetch new private data; revocation cannot erase previously downloaded plaintext.

The relay-encryption recommendation is a **new design obligation**, not a claim that existing transport is encrypted end to end. A backend Ask call receives only the phone-selected bounded evidence under its own consent, as the existing desktop pattern does; it is a separate plaintext-processing boundary from the ciphertext relay. Do not silently send the whole vault or promote legacy PostgreSQL back to memory authority. Until the phone has a verified committed feed and Ask permission, it offers capture and an honest waiting state, not fabricated off-desktop recall.

## Operational and device gates before a live pilot

Verify an owner-controlled HTTPS hostname, DNS, certificate issuance/renewal, fixed client origin, firewall/proxy route, live host storage/capacity and encrypted off-host recovery before accepting relay bytes. The current loopback DO API on port 8001 cannot be used by a phone; the old Caddy overlay is not proof of a live new-profile proxy. Choose and document a bounded encrypted-blob destination, quota and retention period. Test lost-response, upload interruption, desktop offline for days, relay expiry, revocation, restore of old grant DB, concurrent direct Obsidian edit, tombstone, and key loss. A relay backup cannot replace vault backup; restoring old grants requires revocation/reconciliation as DO operations already require.

For iPhone, replace the development bundle ID, establish the owner-approved build/signing/distribution route, permission text and secure-storage behavior, install on an actual iPhone, and prove force-close/outbox retention, foreground transfer and iOS background limitations. Do not claim continuous background sync from an Expo export or PWA. No account is required **inside Recall**, but distribution/signing and hosted TLS/relay are separate operational dependencies. Existing sign-in mobile UI must not be relabeled as the no-sign-in target.

## Exact owner decisions needed before PHONE packet or activation

1. **Association UX and authority:** approve one-time QR with explicit confirmation on the trusted desktop for one named iPhone/workspace/vault and `vault_sync` scope, or choose a manual same-fingerprint method. Decide who can approve a replacement/lost device and where offline recovery material lives. This is distinct from PAIR-01 inference grants.
2. **Transport experience:** approve the recommended authenticated encrypted store-and-forward relay on a reviewed HTTPS host, with desktop as first canonical writer and honest waiting states. A direct-only local-network transfer costs less infrastructure but cannot automatically bridge a phone away from an offline desktop. Off-desktop fresh Ask would be a separate capability decision.
3. **Operations:** approve the exact host/origin, storage quota/retention, off-host backup, TLS/proxy exposure, device-enrollment/revocation operator, and iPhone build/distribution method after readiness checks. No current DO/Supabase plan, certificate, host capacity, Apple signing or live deployment is inferred. Paid storage, distribution and provider use remain unapproved until specified.

No product implementation, private transfer, real invitation, provider call, production activation, migration, deployment, signing or spend follows from this proposal.
