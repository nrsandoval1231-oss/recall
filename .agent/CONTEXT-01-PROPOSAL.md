## Decision and dependency

Build **current context links first**: after a newly captured text/photo source is durably saved, automatic organization can see a small, authorized selection of *current* other vault memories and suggest useful `Related memory` links with evidence on both sides. A shared name is a reason to inspect a candidate, never an identity merge or verified relationship. Put links into the owner-readable Obsidian note and expose the linked source in Recall without asking the user to file or approve each capture. This adds context to the already authorized organization flow; it does not silently widen existing organize consent.

**Historical Ask is a distinct next packet, HISTORY-01.** A current related-memory link is not an answer to “what did I know then?” or “what is latest?” Those questions require an explicit time interpretation, eligible prior revisions, revision timestamps and correction precedence in the Ask evidence contract. Keep R6C and the parent Finish Contract open after CONTEXT-01. Do not label current-only Ask as historical retrieval or assert vague-recall quality from keyword fixtures.

## Proposed bounded build contract

1. Native selects context only from the currently selected vault under its existing lock/recovery/reconciliation/source-verification boundary. Eligibility matches current Ask: active, nonconflicted, verified-source memory with effective human text/correction or an unsuppressed unreviewed proposal. Exclude the new source, removed/missing/corrupt records and stale machine semantics. Send at most eight other memories, each with stable memory ID, revision, source hash, evidence kind/status and an exact bounded excerpt. Include all eligible records when at most eight fit; otherwise use deterministic candidate ranking and return a `selected/eligible/truncated` coverage disclosure. No invented quote, arbitrary path, raw unrelated original or full-vault upload. Persist the exact selected bindings in the organization intent and revalidate them before publishing links.
2. Version the **organize** policy and request/result contract for this newly disclosed prior-vault context. Existing source-only consent does not authorize sending other memories. Require a fresh explicit owner decision before context transmission, while source-only saved capture remains usable. Reuse the same protected `vault_intelligence` grant, purpose-specific consent, operation receipt and provider-budget boundary; do not add an account, separate model router, queue service or second routine inference call. Native supplies context; the provider may propose at most a small bounded set of `related_context` targets among supplied IDs. Backend validates strict IDs, target membership, exact source and target quote substrings, source-local uncertainty, output size and no identity/verified relation assertion. Invalid links are dropped or fail closed; valid source-local extraction still obeys the accepted v1.1 rules. The backend never chooses vault paths, permissions or identity merges.
3. Native commits only a newly versioned, source-bound proposal after checking the original/current note, organization consent decision, selected vault/credential, **every linked target's current revision and evidence**, and the exact receipt. A changed target, direct edit, removal, correction or rename prevents stale link promotion. Preserve old v1–v6 history and renderer bytes; new links require a new format fence and journaled revision. Store target **stable ID plus bound evidence/revision** in vault history; resolve its current note path in the native adapter for Obsidian Markdown and UI navigation. The lifecycle path must keep managed links valid or explicitly suppress/remove them when a target is renamed, removed or corrected; interrupted rewrites recover through the journal, never silently overwrite an Obsidian edit. Human correction of the source suppresses stale context links just as it suppresses current machine semantics. A link is labeled as unreviewed related context, with exact supporting excerpts and originals available; it is never a bidirectional person/entity identity edge.
4. UI shows a short `Related memory` section in the generated Obsidian note and focused Memory Surface. Each link opens the current target and its original evidence, labels uncertainty, and disappears or shows a stale state when native revalidation fails. Capture still confirms the saved original immediately; context failure cannot roll back it. No per-note filing or extra approval step after the newly versioned opt-in.

## Deterministic acceptance and limits

- Synthetic two-source example creates one useful, cautious Obsidian link with both exact quotes and opens the current target/original; a same-name/different-person example creates no asserted identity or factual relationship.
- Zero eligible context, too many candidates, truncated excerpts, offline provider, revoked/outdated consent, budget denial and unknown receipt leave the original and source-local organization truthful; coverage never implies a full-vault conclusion.
- Current source and target edits/corrections, direct Obsidian conflicts, target removal/rename, changed credential/vault, replay and crash at link publication suppress stale links without changing prior format bytes or losing human text/history. Link destinations remain valid after supported rename or are explicitly removed as stale; no dead managed Markdown link is silently left current.
- Shared fixture validates request/result shape and hashes; backend security/schema/provider tests, native vault fault/compatibility tests, client type/lint/unit/build and one local browser journey pass on the exact candidate, followed by independent Sol review. Record commands, results, skips and head identity.
- **Not established here:** historical/as-of retrieval, fuzzy associative retrieval quality, live provider cost/accuracy, installed Windows/iPhone, real handwriting, voice/files/phone transport, migration or whole-product completion. Those remain separately gated.
