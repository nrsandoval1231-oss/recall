## Native repair contract

**Selection is a live revocable session, not a cloned `Vault`.** `LocalVaultState` should issue a cloneable selection guard containing the opaque session token plus stable vault ID and access to the live selection state. Every `schedule_pending` entry (startup, select, capture and explicit process), continuation batch and named recovery must carry that guard; no path may construct a background worker from `Vault` alone. A successful `select_path` revokes the old guard when it replaces the selection, including switch away and back to the same stable vault. Do not hold the selected mutex or vault lock across a network wait. Check the guard before each batch, before receipt GET, immediately before a first POST or permissible same-operation resend, and after each network wait. Final promotion must execute under `LocalVaultState.with(old_session_token, ...)` (or an equivalent short selection lock) so switch cannot interleave between the final session check and journal commit; repeat the existing source/revision/marker/consent/connection/receipt checks inside that boundary. A switch during capability/GET wait causes no later POST or promotion. A POST already begun before a switch has an inherently ambiguous external effect; retain/recover its receipt for accounting but never promote into the unselected vault. Do not mark a definitely unsent operation as a successful upload.

**Keep server wire unchanged; expose local readiness in the native command DTO.** `LocalOrganizationTransport::capability` still parses the exact server `OrganizationCapability` (`vault_id` is the stable vault identity). Native `vault_organization_capability` and `vault_set_organization_consent` return that same server field set plus exactly `local_readiness` and `automatic_enabled`:

```json
{
  "schema_version":"1.0", "scope":"vault_intelligence", "purpose":"organize",
  "vault_id":"<stable vault identity>", "policy_version":"<server value>",
  "provider":"anthropic", "consent":"active", "enabled":true,
  "consent_epoch":1, "decided_at":"<server UTC value>",
  "local_readiness":"ready", "automatic_enabled":true
}
```

`local_readiness` is `ready | needs_setup | off | unknown`. `ready` requires a readable vault marker matching exact stable vault ID, server policy/epoch and the *current* protected connection fingerprint. `needs_setup` means server consent is active but the marker is absent or tied to an older connection/decision; it authorizes **no** upload. `off` means server consent is missing/outdated and no eligible local marker remains; `unknown` covers an unreadable marker, interrupted reconciliation or unavailable exact comparison and also authorizes no upload. `automatic_enabled = server.enabled && local_readiness == ready`; keep `enabled` as the server's existing meaning. A marker mismatch is never silently rewritten by a capability GET. If revoked server consent leaves a marker that cannot be cleared, report `unknown`, not `off`. Native validates the server `vault_id` against the selected stable identity and returns no capability for a changed session.

**Repair the server-decision/local-marker gap explicitly.** Add one native command `vault_reconcile_organization_consent(expectedVaultId) -> native capability DTO`; no backend endpoint or schema change. It must use the current selected-session token and protected grant, GET the current exact server decision, then under the selected vault lock write a **new** marker with a fresh local epoch only when current consent is active and policy/vault/fingerprint match. This command is invoked by an explicit `Finish setup` action after the disclosure, including after a server-success/local-write failure or re-pair. The marker becomes the serialized *future-capture* fence at its actual commit; captures committed before it remain unqueued. If server consent is missing/outdated, the same command may clear a stale marker but never create one. A marker read/write error returns `unknown` with a retryable local explanation; it does not revoke server consent or claim organization is on. Existing queued intents from a different local/server epoch remain stale, never revived. This command cannot start a provider request or sweep old captures.

For `vault_set_organization_consent`, an ambiguous POST is resolved only if authenticated GET proves the **requested decision** at `expected_consent_epoch + 1` with the current policy: requested `true` requires `consent=active`; requested `false` requires `consent=missing`. Do **not** compare `capability.enabled` with requested `enabled`: that field also depends on provider configuration and the feature flag, so valid saved consent can coexist with `enabled=false`. An unchanged epoch, a later/different epoch, `consent=outdated` or failed GET is `unknown`; never treat it as consent success or blindly repeat POST. A confirmed enable followed by marker-write failure returns/reloads `needs_setup` or `unknown`, preserving a visible `Finish setup` path. Revocation remains possible while the provider feature flag is disabled; server denial precedes local marker clearance and prevents upload if the local write fails. Re-pairing changes the fingerprint, so even a surviving server decision requires the explicit fresh local fence.

## UI contract after native handoff

`selected.vault_id` is an opaque **invocation session token**; `selected.vault_identity` is the stable identity expected in the native capability's `vault_id`. Pass both to `OrganizationSettings`: use the former only for commands, compare every capability/consent/reconcile response to the latter. Retain existing generation guards for late UI results. Show `Automatic organization is on` only for `automatic_enabled`. When server consent is active but `local_readiness=needs_setup`, say the saved permission needs finishing on this device and offer `Finish setup`; new captures stay local until that action succeeds. For `unknown`, explain that local status is unresolved and offer `Check again`/retry without claiming on or off. Keep `Turn off` available when server consent is active, even if local setup is incomplete or service processing is unavailable. A valid native-shaped fixture must use *different* session and stable IDs, and test capability, opt-in, failed local marker, explicit reconciliation, revocation and vault switch.
