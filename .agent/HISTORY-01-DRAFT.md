# HISTORY-01 implementation draft — recorded-then Ask

**WAITING on CONTEXT-01 independent acceptance and its current FIX repairs.** This is an implementation-ready contract for the next bounded packet, not authorization to activate consent, call a provider, migrate a live database, deploy, push or claim historical recall accepted. Preserve the current dirty candidate. Canonical product requirement: natural current/historical recall with exact source evidence, human corrections and vault history; this first slice handles anchored recorded-as-of questions without inventing event-time truth.

## One direction

Extend the accepted Ask route and receipt/provider path with a strict v2 historical request, one native vault-history selection operation and a small Ask-panel clarification flow. Keep v1 current Ask byte-compatible. Do not add a vector service, historical index, new provider call, vault format, mobile scaffold or native rename operation. The backend receives only the bounded selected excerpts; the Obsidian vault remains authority for revisions and originals.

## Scope and consent decision

The existing `vault_intelligence_ask_consents` row is **workspace purpose consent**, with `enabled`, `policy_version` and monotone `version`; the current bearer grants are independently exact `(workspace,device,vault)` and rechecked before retrieval, before provider dispatch, at receipt return and at GET recovery. Reuse that boundary. A v1 row at `ai_policy_version` continues to authorize **current Ask only**. A newly explicit owner decision upgrades the same row to `ask-history-v1|<ai_policy_version>`; the UI discloses that this workspace Ask purpose may send selected **retained revisions** from any vault whose device already has its own owner-approved `vault_intelligence` grant. This opt-in does **not** pair a device, create a grant or give another workspace access. The versioned history decision also authorizes v1 current Ask. History opt-out returns the row to the base policy while leaving current Ask enabled; turning off Ask itself still revokes both. Each policy/version change invalidates prior in-flight or stored receipts under the existing fail-closed receipt check, including current Ask requests started before an upgrade. UI should warn when a pending Ask exists; do not retry a sent operation with a changed payload. This is the smallest truthful use of the existing workspace purpose row; per-vault historical consent is a separate future policy choice, not silently claimed here.

Add a protected `POST /v1/local-intelligence/ask/consent` solely for this transition. Authorization and owner/first-workspace check occur **before reading the body**. Strict body: `{"enable_history":true|false,"expected_version":N}`, `N>=0`; server chooses the exact current policy string and rejects stale version with conflict. `true` requires an existing active base/current Ask decision or existing history decision; no implicit first-use current Ask consent. `false` returns an active history decision to the base Ask policy. Return the extended capability, `Cache-Control: no-store`; failure/unknown outcomes require a fresh capability read before retry. Existing `set_ask_consent` and owner revocation remain. Extend GET capability without changing its current `scope`, `consent`, `enabled` meanings: add `history_consent: "active"|"missing"|"outdated"`, `history_enabled: bool`, `consent_version: int` (0 if absent), and `history_policy_version` (server-chosen string). Disabled provider/config can yield `history_consent=active` with `history_enabled=false`. Native capability checks exact selected session and confirmed grant as today; UI sends this POST only after the user's explicit disclosure action. No saved local marker or future-capture fence is needed for a user-initiated Ask.

## Deterministic question routing

Current/latest questions retain v1. Only a small **unambiguous** grammar routes to history: `as of <full date>`, `what did I know on <full date>`, `what had I recorded by <full date>`, and `what changed since <full date>`. Accept ISO `YYYY-MM-DD` or English month-name/day/year, plus `yesterday`/`today` relative to the device's local calendar date. Numeric slash dates, yearless dates, timezone abbreviations, multiple competing dates, unanchored “then/before/at that time,” and event-only references return an inline conversational clarification **before creating an operation ID, intent or network request**. A follow-up entered in the same Ask box can supply the date in ordinary language; no date picker or revision ID is mandatory. The parser must not treat any incidental date in an ordinary topical question as historical intent. “Latest/now/current” stays v1. Historical phrases outside this grammar are explicitly a remaining retrieval gap, not answered from current text as if past.

The Ask UI computes `start_utc` and `end_exclusive_utc` from the selected local calendar day using platform `Date`/`Intl`, displays the device timezone, and freezes both instants and the original question in the local pending intent before dispatch. For the synthetic `2026-10-01` day in `America/Chicago`, end exclusive is `2026-10-02T05:00:00Z`. Reject invalid dates, a failed timezone lookup, unexpected local-date normalization, or ambiguous timezone text. DST day length may be 23, 24 or 25 hours. Native validates strict second-resolution UTC RFC3339 (`YYYY-MM-DDTHH:mm:ssZ`), `start < end`, bounded 23–25-hour calendar-day span, and the history mode before selection; it does not trust the UI to choose files, evidence or a path. The UTC interval is user intent, not an authorization credential. Recovery uses the persisted interval verbatim, never the device's later clock/timezone. Native event `recorded_at` is UTC second-resolution and is compared to the **exclusive** end; equal-second journal ordering uses revision number. If the relevant revision chain has malformed or decreasing recorded times, omit that memory with an explicit limitation rather than infer a chronology.

## Request, receipt and enforceable answer contract

Keep `POST /v1/local-intelligence/ask` and `GET /v1/local-intelligence/ask/{operation_id}`. V1 request/receipt remains byte-compatible. V2 adds required `temporal` and fields to each existing evidence item, with the same 32-KiB total body, eight-item and 1,500-UTF-8-byte excerpt limits:

```json
{
  "schema_version": "2.0", "operation_id": "00000000-0000-4000-8000-000000000011",
  "vault_id": "00000000-0000-4000-8000-000000000002",
  "question": "What did I know on October 1, 2026?",
  "temporal": {"mode":"as_of","start_utc":"2026-10-01T05:00:00Z","end_exclusive_utc":"2026-10-02T05:00:00Z","display_date":"2026-10-01","display_timezone":"America/Chicago"},
  "coverage": {"eligible_count":1,"selected_count":1,"limited":false,"truncated_count":0},
  "evidence": [{"citation_id":"c1","memory_id":"00000000-0000-4000-8000-000000000003","memory_revision":2,"event_sha256":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","source_sha256":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb","captured_at":"2026-09-30T12:00:00Z","recorded_at":"2026-10-01T12:00:00Z","current_revision":3,"history_status":"as_of","evidence_kind":"human_note","epistemic_state":"reported","excerpt":"The remembered wording at that revision."}]
}
```

`mode` is `as_of` or `compare_to_current`; the latter is used only for “what changed since ...”. `history_status` is exactly `as_of`, `as_of_later_corrected`, or `current_counterpart`: it describes the evidence item's **role in this question**, not whether the same revision is still latest. Thus an as-of item can equal `current_revision`; the UI recomputes that present status on display. V2 permits at most two items per memory, with distinct `(memory_id,memory_revision,evidence_kind)` and ordered `c1`–`c8`; `as_of_later_corrected` requires a same-memory `current_counterpart`, and a comparison requires one of each role for every included memory. `coverage` counts eligible **items**, including required current correction counterparts, and limitation text states when the eight-item window or any excerpt truncation narrows the answer. `event_sha256` identifies the exact immutable journal event bytes; `source_sha256` still identifies the original. Backend strictly rejects unknown/duplicate keys, invalid UUIDs/hashes/timestamps/statuses, floats/nonfinite numbers, non-UTF-8, oversized bounds and changed canonical digest. Use existing recursive sorted-key UTF-8 compact JSON SHA-256/idempotency rules and receipt `schema_version: "1.0"`; the stored payload hash binds the entire v2 request. The backend maps `recorded_at` and `history_status` into the existing provider evidence packet and reserves the same one-call token budget. No result body or historical excerpt is returned from a receipt after scope/consent change; GET 404 stays no-receipt and expiry remains a tombstone, never permission to resend.

Under **one vault lock**, native recovers/reconciles journal state, validates event/hash chain and original, and selects the highest eligible revision with `recorded_at < end_exclusive_utc` for each currently active, conflict-free, source-verified memory. It uses the revision's human note or effective human reading correction first; an unsuppressed machine reading is `unreviewed`, not a verified fact. Any later human correction to selected machine content, or any changed effective human note/reading text, must be accompanied by the current counterpart item or that historical claim is omitted. For `compare_to_current`, pair selected past and current revisions for each included memory; no unsupported pair is truncated into a one-sided change claim. If fewer than eight eligible items exist, include all; otherwise deterministic ranking and coverage disclosure apply. Select query-near excerpts as exact UTF-8 substrings. Deleted/missing/conflicted memories do not become historical private answers through this route. This is recorded-vault state, not proof that a proposition was true on that date.

The provider returns the existing `{status,sentences,limitations}` shape. Backend can **enforce citation IDs, counts and status composition**, not the semantic truth of free-form prose. For `as_of`, every answered sentence must cite at least one `as_of` or `as_of_later_corrected` item; any sentence citing `as_of_later_corrected` must also cite its paired current correction. For `compare_to_current`, every answered sentence must cite both an `as_of` or `as_of_later_corrected` item and its `current_counterpart` from the **same memory**; if it cannot, downgrade to `insufficient_evidence`. Do not claim a generic natural-language detector can prove whether prose asserts a change. Native independently validates the receipt against the persisted v2 evidence and adds mandatory coverage/truncation/recorded-time limitations. Answer citations are constructed from that persisted evidence, not model-supplied quote/path/revision fields. On click, a narrow native history-citation command revalidates selected session, complete event chain, exact event/source hashes, excerpt membership and current state under one lock; it returns that retained revision alongside the original source. UI labels “Recorded then,” “Later corrected,” or “Current” from bound/rechecked status. A quote from a past human note is identified as that note revision, not as original attachment text.

Before POST and before displaying GET/POST completion, revalidate grant/fingerprint, selected session, consent policy/version, source, every selected event/excerpt and current revision/status. Any changed correction/current state yields `STALE_EVIDENCE` with no answer; never reselect under the same operation ID. The prepared v2 intent is written before network dispatch, and `unknown` recovers only the original digest/operation. A resolved clarification never triggers a hidden second paid request.
