# HISTORY-01 capability compatibility addendum

**Active packet correction.** The accepted native current-Ask transport deserializes `GET /v1/local-intelligence/capability` into `AskCapabilityReply` with `serde(deny_unknown_fields)`. Adding history fields to that unnegotiated response would make an older desktop report current Ask unavailable when only the service had updated. Preserve that route's successful JSON shape **exactly** as `{ "scope": "vault_intelligence", "consent": "active"|"missing", "enabled": boolean }`. Its current-Ask meaning remains unchanged.

The new native client explicitly calls a separate protected `GET /v1/local-intelligence/history-capability`. Its successful JSON has exactly `{ "scope": "vault_intelligence", "history_consent": "active"|"missing"|"outdated", "history_enabled": boolean, "consent_version": integer, "history_policy_version": string }`. `POST /v1/local-intelligence/ask/consent` returns that **same history-only DTO** after the strict owner/version decision; it does not add fields to the legacy capability response. Both routes authorize the exact `(workspace,device,vault)` intelligence grant before response or request body; POST also checks owner before body. `history_enabled` includes service/provider availability; `history_consent` reports the purpose decision independently, so disabled runtime never masquerades as revoked consent. Use `consent_version=0` when no row exists.

New native transport keeps its existing `capability()` method and strict legacy reply unchanged, adds `history_capability()` and `set_history_consent()` with separate strict response validation, and composes them only at the UI command boundary. A failed/unsupported history capability is **unknown/unavailable for historical Ask only**; current Ask remains usable. History dispatch requires a fresh successful history capability and confirmed grant. No fallback to v1 Ask for a historical question. This avoids negotiated headers/query variants and does not require a general authentication change.

Native file ownership is expanded mechanically to `apps/desktop/src-tauri/src/local_intelligence_transport.rs` and its focused tests for the two new calls and v2 transport. Backend tests must assert an older strict client can still decode the exact three-key legacy JSON after server upgrade, and that the separate history GET/POST DTOs reject missing/extra keys and check scope before body. The backend-owned synthetic wire fixture includes both capability shapes. Existing v1 request, receipt, consent and journal bytes remain compatible.
