## Objective and authority

After one explicit, remembered opt-in for **automatic cloud organization of future text and photos**, a user saves a note or photo and returns immediately to their memories. Recall durably saves the original in Obsidian first, then interprets it while the desktop runs, publishing a useful structured Obsidian note with evidence, uncertainty and history. No routine filing or per-note organization approval. The user can keep capturing locally with no account or remote connection; queued, processed and failed states are honest. This is the smallest new organizer across text and photo, not voice, files, phone transport, cross-note identity linking, migration, or live acceptance.

The `vault_intelligence` owner/device/vault credential is the only eligible network grant. Its existing Ask purpose and consent do **not** authorize organization. The older `photo_inference` grant, per-photo consent and `/v1/local-readings` contract remain unchanged. Add an independently versioned, revocable `organize` consent that explicitly names: future typed text and saved photo bytes, the configured provider, source-local extraction, bounded cloud processing, and no automatic processing of the pre-opt-in backlog. Default off. A scope-specific settings action may set/revoke this consent after explicit UI disclosure through the already owner-associated device; no public self-enrollment. A server-side capability check and consent recheck gate every dispatch. This packet builds code and synthetic validation; it does not issue a real grant, enable consent, send a live provider request, spend, deploy, merge, or migrate real data.

## Capability and remembered consent wire v1

Independent-review repair amendment: the server capability wire below remains unchanged. Native capability and consent commands return those server fields plus `local_readiness` (`ready`, `needs_setup`, `off`, `unknown`) and `automatic_enabled`. Only a current matching local marker makes readiness `ready`; `automatic_enabled` also requires server availability. `vault_reconcile_organization_consent(expectedVaultId)` explicitly finishes interrupted local setup with a fresh future-only fence, never backfill. Invocation uses the opaque selection token; response `vault_id` is compared against the permanent vault identity. Every background batch/recovery carries a revocable selection guard; final journal promotion is atomic with the selected-session check. Exact repair contract and tests are in [REPAIR-ARCHITECTURE](ORGANIZE-01/REPAIR-ARCHITECTURE.md); initial candidate and independent FIX are preserved under `ORGANIZE-01/first-review/`.

Architecture clarification: store organization consent under `(workspace_id, device_id, vault_id)` and filter every decision, lock and recheck by the exact authenticated grant tuple. One associated desktop/vault opts in independently; its decision must neither authorize nor invalidate another association's queue. Workspace RLS and the owner check still apply. Re-pairing requires a fresh local connection-bound marker. Ask's existing consent scope is unchanged. This clarification changes no wire fields and is covered by cross-device/vault epoch-isolation tests.

The inference service adds `GET /v1/local-intelligence/organization-capability` and `POST /v1/local-intelligence/organization-consent`, both authenticated with the exact owner-associated `vault_intelligence` bearer before any private response or POST body read. The current policy version is server-generated as `organize-v1|<ai_policy_version>|<ai_model_id>` (configuration rejects a value over 160 UTF-8 bytes); changing the material sent, provider/model or purpose increments the `organize-v1` component or its inputs and requires fresh consent. Native echoes the returned string exactly; neither renderer nor native constructs a substitute. A capability response has exactly:

```json
{
  "schema_version": "1.0",
  "scope": "vault_intelligence",
  "purpose": "organize",
  "vault_id": "00000000-0000-4000-8000-000000000002",
  "policy_version": "organize-v1|anthropic-v1|configured-model",
  "provider": "anthropic",
  "consent": "active",
  "enabled": true,
  "consent_epoch": 1,
  "decided_at": "2026-10-09T12:00:00Z"
}
```

`consent` is `active`, `missing`, or `outdated`; `enabled` requires active consent, the feature flag, configured provider and current grant. Before the first decision, `consent_epoch=0` and `decided_at=null`. A revoked row reports `missing` and its incremented epoch. `provider` is `anthropic` or `null` when unconfigured. `decided_at` is server UTC audit time only. POST accepts at most 1024 bytes of strict JSON with exactly `{ "schema_version": "1.0", "policy_version": "<value returned by GET>", "enabled": true | false, "expected_consent_epoch": <nonnegative integer> }` and returns the complete capability object. Server checks the epoch transactionally, records the owner decision with monotonically incremented `consent_epoch`, and rejects stale policy/epoch; after an ambiguous response, native GETs capability before any repeat POST. `enabled=false` revokes this purpose alone and does not revoke Ask, photo reading or the underlying device grant. The service rechecks matching active policy/epoch before reservation, before provider dispatch and before returning result content. No default opt-in or silent backfill.

Native UI commands are `vault_organization_capability(expectedVaultId) ->` the capability object above, `vault_set_organization_consent(expectedVaultId, enabled, expectedConsentEpoch) ->` that object, `vault_organization_operations(expectedVaultId, memoryId) ->` current bounded operation states, and `vault_recover_organization(expectedVaultId, operationId) ->` the bound receipt/outcome after native revalidation. Renderer supplies no policy string, bearer, endpoint, source bytes or arbitrary operation body. UI implementation waits for the native handoff but uses these names and fields, rather than inventing a second consent contract.

## Source-first transaction and local operation

`vault_capture_text` and `vault_capture` must return only after the immutable source and initial human note/revision are committed through the existing journal. A successful capture after remembered organize consent creates one native operational intent under `Recall/_meta/organize/<operation-id>.json`, bound to stable vault identity, source/memory ID, source SHA-256, current revision, current human text digest, source kind, `consent_epoch` and protected connection fingerprint. This file contains no credential, provider output or arbitrary path; it is private retry state, not a canonical memory/history revision. A failed/unknown organizer never rolls back the saved original. Consent applies to **new captures after opt-in**, not a silent sweep of old vault sources.

Use a small opportunistic runner invoked after capture and on desktop startup/refresh, while Recall is open. After the server confirms opt-in, native writes a vault-local marker with stable vault ID, exact policy version, server `consent_epoch` and a new local epoch UUID under the same vault lock used by capture. A capture is *future* only if it enters that serialized boundary after the marker: write a prepared intent bound to the capture operation before committing the source, then mark it eligible only after the immutable source and history receipt validate. A crash between source commit and intent completion is recoverable from the prepared intent; a dangling intent without a committed source is never dispatched. Backend `decided_at` and client `captured_at` are never compared, so clock skew cannot enroll older notes. Each intent carries both epochs. On each future capture the marker permits local queuing, while live capability/consent and matching server epoch are checked again before dispatch. It enumerates bounded pending intents under the selected vault, checks current capability and source state, and advances one safe operation at a time. It is not an always-on job framework. Offline or disabled service leaves the local record at `saved_local`/`queued`. States shown to UI: `saved_local`, `queued`, `processing`, `organized`, `failed`, `unknown`, `stale`; `unknown` first recovers the same receipt and never blindly issues another paid call. On revoke, server increments the epoch first; native then clears its marker under the vault lock. If local clearing is interrupted, server denial still prevents upload and UI reports an unknown local marker until reconciled. Old unsent intents are marked `stale`/`saved_local`, never reactivated by later opt-in (which creates another epoch); sent intents may be recovered for accounting but cannot promote content after revocation. Originals stay local.

## Exact organize wire v1

Native calls `POST /v1/local-intelligence/organizations` with the **new `organize` purpose** under its protected `vault_intelligence` bearer. Authenticate scope and organize consent before reading body. The request uses `X-Recall-Organization` containing compact, strict UTF-8 JSON (at most 4096 bytes) with exactly these keys; the body is raw selected input bytes, never a renderer-selected file path:

```json
{
  "schema_version": "1.0",
  "operation_id": "00000000-0000-4000-8000-000000000011",
  "vault_id": "00000000-0000-4000-8000-000000000002",
  "memory_id": "00000000-0000-4000-8000-000000000003",
  "source_kind": "text",
  "source_sha256": "539af3d58bddb200f121147c9940a00382dc32cd1ff0d87507eef6a238b7c53c",
  "expected_revision": 1,
  "input_sha256": "539af3d58bddb200f121147c9940a00382dc32cd1ff0d87507eef6a238b7c53c",
  "consent_epoch": 1,
  "captured_at": "2026-10-09T12:00:00Z"
}
```

For `text`, `Content-Type: text/plain; charset=utf-8`, the body is the exact **current human text** (initially the saved typed note), `input_sha256` is its byte hash, and `source_sha256` remains the immutable original attachment hash; these may differ after a supported edit. The native adapter validates both against the vault. Text must be valid UTF-8, nonempty, at most 30,000 Unicode characters and within a bounded HTTP size that fits the v1.1 extraction schema's 30,000-character transcription. Larger text still saves locally and displays `saved_local` with a clear organizer limit; it is never silently truncated and called fully organized. For `photo`, the body is the immutable verified PNG/JPEG/WebP original (at most the existing 25 MiB bound), `input_sha256 == source_sha256`, and `Content-Type` matches verified bytes. The service makes the bounded JPEG derivative internally as the current selected-photo path does; no original bytes are stored there.

The service verifies exact header shape/UUID/hash/revision/date/type, current organize consent epoch, body length/hash/MIME/UTF-8 or image decode before budget reservation. The idempotency digest is SHA-256 of strict canonical JSON over `{binding, media_type, input_sha256}` with recursively sorted keys, UTF-8 non-ASCII, compact separators and no floats; reuse the Ask Python/Rust canonicalization and add a shared Unicode golden fixture. For the sample binding above, `Content-Type: text/plain; charset=utf-8` and body `Example typed note`, the source/input SHA-256 is `539af3d58bddb200f121147c9940a00382dc32cd1ff0d87507eef6a238b7c53c` and the canonical payload digest is `788359b830dec7814724751fcd938963e2c67e57fbc827403a55d651562cf1f5`. `(workspace, device, vault, operation)` plus digest is unique. Same digest returns the prior receipt; different digest fails. `GET /v1/local-intelligence/organizations/{operation_id}` authenticates before lookup and returns the same receipt. An authenticated 404 means no receipt; terminal `expired` means no resend; `unknown` and failed GET block resend. A POST retry needs the same bytes/binding and fresh native source/revision/connection/consent validation.

## v6 vault projection and correction precedence

Add an optional `organization` field to `VaultMemory`/stored event, allowed only in new `recall-local-vault-v6` events. It holds the exact binding, validated normalized result, source-kind-specific derivative metadata and `review_state=unreviewed`; it is a proposal, not an owner-confirmed fact. `kind=organization` increments the memory revision and journals a new Markdown publication only after native revalidates current selected vault, source bytes/hash, current revision, human note hash, existing photo reading correction, consent/connection and complete matching receipt. It cannot change `memory.note`, immutable source, existing `reading`, IDs, or a human correction. Old v1–v5 event/history bytes and renderer output stay byte-compatible; a retained previous manifest and v6 writer fence make downgrade fail closed. Direct Obsidian edits still reconcile through the managed human region; generated region edits conflict without overwrite. Retry/recovery uses stored predecessor bytes for parent hashes and retains conflict evidence.

The v6 renderer creates ordinary Obsidian properties, a readable summary, source-local mentions/statements/suggested actions/uncertainties and links to the correct original (`.txt` or image), with machine proposals visibly unreviewed. When `organization` is absent, v6 preserves the existing v5 text or v4 photo Markdown projection; no read-time rewrite of older notes occurs. The human-editable section remains at the end for conflict-safe reconciliation. Evidence links for a text interpretation of an edited note identify the **current human note** as their provenance, rather than pretending a quote absent from the immutable original exists there. No name match creates a cross-note identity link. Search and Ask may use supported current machine fields only while the proposal remains effective.

An edit/correction during processing makes the result `stale` and blocks promotion. After promotion, any later `correct`, `external` or `reading_correction` history event suppresses that proposal's current generated semantics/search/Ask projection; preserve the original proposal in history. Reprocessing may create a new proposal bound to the revised human text, but never resets the human correction or marks machine content verified. Tombstones, missing notes, conflicts and damaged source hashes are ineligible. Keep existing photo reading/correction history intact; the old one-photo action remains separate, and the UI should not invite duplicate paid processing for an already effective organization.
